# ARCHITECTURE.md

The architecture document for this repository, following the
[architecture.md](https://architecture.md) schema — built so an agent (or a
new colleague) can comprehend the repository from this file alone, and so this
repository's own architectural principles (expressed for Laravel below) are
visible in how it actually works. Fill every section; update it in
the same change that alters the architecture it describes.

This repository is a **cross-cutting starter**, not a complete application.
It carries the shared tooling and configuration; the application tree itself
is generated by `laravel new` and merged in (see §1 and §6).

## 1. Project Structure

This repo holds the files every Laravel project shares. The application
skeleton (`app/`, `routes/`, `config/`, `database/`, `resources/`, `public/`,
`bootstrap/`) is produced by `laravel new` and rsynced in; this repo
deliberately does not contain it, so the cross-cutting concerns can be
updated and shared without carrying a stale app tree.

```
laravel-skeleton/                 # this repo: cross-cutting concerns
├── composer.json                 # PSR-4 Lines\Skeleton\ → app/, dev tooling
├── phpunit.xml.dist              # Pest/PHPUnit config (Unit + Feature suites)
├── rector.php                    # Rector paths: app/ + tests/
├── eslint.config.js              # prettier-only, for the JS assets
├── package.json                  # Vite, Tailwind, Playwright, Blade/Tailwind prettier
├── vite.config.js                # asset pipeline
├── .blade.format.json            # Blade formatter config
├── phpunit.xml.dist
├── devshell/                     # git submodule: devshell-php
└── .github/                      # changelog + automatic-updates workflows
```

**Where the logic lives** (the structure a consumer app follows): a use case
is an **action** (`App\...\Actions\*Action`,
invokable, DTO in → model out); a readonly **DTO** (`*Data`) crosses the UI
boundary; **models** are lean data + identity (no calculations in
accessors); a computed value is calculated by an action and stored; repeated
query logic moves to a `*QueryBuilder`, repeated collection logic to a
`*Collection`. The UI (Filament/Livewire) reaches the domain only through an
action + DTO. Domain code never imports the UI.

### Ports & adapters

Not defined in the starter. A consumer app follows the hexagonal-flavored
layering stated here: the **domain** owns the ports it needs when a
real external seam exists, `Infrastructure/` holds the adapters, and the
composition root is the app's `ServiceProvider` (and each module's
`*ServiceProvider`). The lean guardrail applies — a port is added when a
second implementation or a real external dependency appears, never
speculatively.

## 4. Data Stores

- **Application database** — owned by the consumer app (Laravel default:
  SQLite/MySQL/PostgreSQL). Not present in the starter.
- **Test database** — SQLite `:memory:` (`phpunit.xml.dist`, `DB_CONNECTION
  sqlite`, `DB_DATABASE :memory:`), so tests are isolated and disposable.
- **Cache/queue/session** — set to `array`/`sync` in the test environment;
  the app's real drivers are configured per project.

## 5. External Integrations / APIs

None in the starter. The tooling integrates Composer (Packagist), npm/pnpm
(Vite/Tailwind/Playwright) and the Nix devshell; a consumer app adds its own
third-party integrations, each behind a port (§12).

## 6. Deployment & Infrastructure

- **Consumption**: create a project repo, add this as a secondary remote
  (`git remote add skeleton git@github.com:99linesofcode/laravel-skeleton.git`),
  `git fetch skeleton`, `git rebase skeleton/main`, then `rsync -ac
  tmp_dir/ project_dir/` to merge the `laravel new` output. Updates flow the
  same way; `git diff` shows what to keep or toss.
- **Local environment**: the `devshell` submodule (`devshell-php`) via
  `.envrc` → `use flake ./devshell`; `direnv allow` to activate.
- **CI/CD**: GitHub Actions — `changelog.yaml` (on push to `main`) and
  `automatic-updates.yaml` (Dependabot/agent updates on PRs). The shared
  `.github-php` starter provides the `test.yaml` and `deploy.yaml` reusable
  workflows a consumer copies in.
- **Monitoring/logging**: app-owned; nothing in the starter.

## 7. Security Considerations

- **Secrets**: `.env` files are git-ignored (`.env`, `.env.backup`,
  `.env.production`); `.env.example` is the committed template, and
  `php artisan key:generate` mints the app key in the setup script.
- **Generated artifacts**: `_ide_helper*.php`, `.phpstorm.meta.php` and
  `phpstan.neon`/`phpunit.xml` (local copies) are ignored.
- **Dependencies**: Dependabot covers Composer, npm and the devshell
  submodule; `composer.lock` is tracked.
- No credentials or runtime attack surface live in the starter.

## 8. Development & Testing Environment

- **Local setup**: `direnv allow` for the devshell; then the Composer
  `setup` script (`composer install`, copy `.env`, copy `phpunit.xml`,
  `artisan key:generate`, `artisan migrate --force`, `pnpm install`,
  `pnpm exec build`).
- **Testing**: Pest 4 with `phpunit.xml.dist` (`Unit` and `Feature` suites;
  a commented `Browser` suite for Playwright). `php artisan test` or
  `vendor/bin/pest`.
- **Code quality**: **Pint** (formatting), **PHPStan via Larastan**
  (`analyse`), **Rector** (refactors). Composer scripts: `lint` (Pint
  `--test` + PHPStan + deptrac), `format` (Pint + PHPStan `--fix` + Rector),
  `refactor`, `analyse`, `dev`.
- **Mechanical gates** (and what each makes impossible):
  - `composer lint` — Pint formatting check plus PHPStan analysis; a style
    or type violation fails before review.
  - **Pest** — behavioral tests; a broken action or DTO fails the suite.
  - **Rector** — mechanical modernisation; dead code, missing type
    declarations and naming drift are corrected rather than debated.
  - **Boundary gate**: **deptrac** is the PHP boundary gate (the language
    equivalent of `eslint-plugin-boundaries`) — the layer contract
    (`App`/UI → `Domain` → `Infrastructure`; `Domain` imports no UI;
    `Infrastructure` implements ports the domain owns) is the rule it
    enforces. Wired into `composer lint` and the `analyse` workflow; layers
    match by namespace, so the rules hold wherever a consumer puts the code.
    The composition root (the `*ServiceProvider`) sits outside the layers on
    purpose: it is the one place wiring happens.

## 9. Future Considerations / Roadmap

**Deliberate non-goals:**

- **Not a complete application.** The `laravel new` output is merged in by
  the consumer; the starter carries only cross-cutting concerns.
- **No ecosystem-neutral concerns.** `.editorconfig`, `.prettierrc`,
  `.gitignore` and `.ignore` come from `git-skeleton` via rebase — they are
  not duplicated here.
- **No custom architecture beyond the standard recorded here.** Actions +
  DTOs, lean models, custom query builders/collections, no repository over
  Eloquent unless a real storage-swap seam exists.
- **`Infrastructure/` stays empty until needed.** No speculative ports or
  adapters.
- **No `Utils/`/`Helpers/` dump.** Generic, framework-grade code goes to
  `shared/`/`Support/` on its way to extraction.

**Known debt / open items**: `phpunit.xml.dist`'s `<source><include>`
currently points at `src` while the PSR-4 root is `app/`; a consumer that
uses `app/` should align it. `rector.php` already points at `app/` and
`tests/`. `composer lint`'s PHPStan leg needs a `phpstan.neon` (or explicit
paths) — the starter ships neither, so that leg fails until a consumer adds
the config with its merge; Pint and deptrac run green on the bare starter.

## 11. Glossary / Acronyms

- **Skeleton** — a starter consumed via a secondary git remote and rebase.
- **PSR-4** — the PHP autoloading standard; here `Lines\Skeleton\` → `app/`.
- **Action** — an invokable use case, `*Action`; the single seam the UI calls.
- **DTO** — a readonly data transfer object, `*Data`, extending the shared
  base with `casts()`.
- **Larastan** — PHPStan's Laravel extension, used for static analysis.
- **Pint** — Laravel's opinionated PHP formatter.
- **Rector** — automated PHP refactoring.
- **Pest** — the test framework (BDD-style) with a Testbench integration for
  packages.
- **deptrac** — the PHP dependency-boundary analyser; the layer gate.
- **Devshell** — a `nix develop` environment (`devshell-php`).

## 12. Conventions & Boundaries

The house standards this repository adheres to — stated here in full; this
section records what is enforced **here**.

- **Folder structure**: PSR-4. This starter autoloads `Lines\Skeleton\` →
  `app/`; a module/package uses `Lines\<Module>\` → `src/` with the
  hexagonal-flavored layering `App/` (UI) / `Domain/` / `Infrastructure/`.
  The path locates the layer and module; the name locates the role.
- **File naming**: role suffixes — `*Action`, `*Data`, `*Status`, `*Factory`,
  `*ServiceProvider`, `*QueryBuilder`, `*Collection`, `*Event`, `*Rule`.
  Models stay bare (`Post`, never `PostEntity`). One class per file.
- **Entry point**: Laravel's conventional `public/index.php` + `artisan`;
  for a module/package, the `*ServiceProvider` is the composition root —
  the one place wiring and interface bindings happen.
- **Dependency direction**: `App` (UI) → `Domain` → `Infrastructure`;
  `Domain` imports no UI (Filament/Livewire); `Infrastructure` implements the
  ports the domain owns; UI never calls Eloquent directly. Enforced by
  **deptrac**, the boundary gate — a naming standard without a gate erodes
  one change at a time.
- **Actions carry the logic**: every user story is an invokable action taking
  a DTO; actions compose actions; dependencies are constructor-injected
  (never `app()`/`resolve()` inside a body); multi-write operations are
  wrapped in `DB::transaction()`.
- **Canonical DTOs**: one readonly DTO per domain concept, owned by the core
  (`*Data`, extends the shared base, `casts()` for coercion); raw provider
  shapes are mapped at the boundary and never cross into the domain.
- **Lean models**: data + identity only; no calculations in accessors;
  named scopes become `*QueryBuilder`s; repeated collection logic becomes a
  `*Collection`.
- **Tooling**: Pint formatting, Larastan/PHPStan analysis, Rector refactors,
  Pest tests — wired through the Composer `lint`/`format`/`refactor`/`analyse`
  scripts.
- **Documentation surfaces**: WHY comments at the change site; a change that
  alters the structure or the shared toolchain updates this file in the same
  change.
